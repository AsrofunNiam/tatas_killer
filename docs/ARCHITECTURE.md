# Architecture

## Overview

Tatas Killer uses a Tauri v2 architecture. React renders the desktop interface and requests privileged local operations through registered Tauri commands. Rust owns all process discovery, filesystem inspection, resource sampling, termination, and restart behavior.

```text
React UI
  | invoke(command, payload)
  v
Tauri command boundary
  |
  +-- Windows listener adapter (netstat)
  +-- Process snapshot and metrics (sysinfo)
  +-- Project recognition (manifest inspection)
  +-- Process control (taskkill / validated restart)
  v
Operating system
```

The frontend never constructs raw shell commands.

## Runtime components

### React frontend

`src/App.tsx` currently contains the application view and state:

- active view, search, filters, and accordion state;
- selected PIDs and bulk actions;
- process-tree loading;
- resource polling every two seconds;
- persisted light/dark preference;
- calls to the Rust command boundary.

`src/App.css` defines theme tokens, responsive layout, cards, trees, status chips, and action styles.

As the UI grows, these responsibilities should move into `components/`, `hooks/`, and `types/` modules.

### Rust backend

`src-tauri/src/lib.rs` currently provides:

| Command | Purpose |
| --- | --- |
| `scan_active_ports` | Discover TCP listeners and enrich them with process/project metadata. |
| `get_process_metrics` | Return aggregated CPU/RAM metrics for listener runtime trees. |
| `get_process_tree` | Build an on-demand dependency tree around a listener PID. |
| `kill_process` | Stop one validated process tree. |
| `kill_workspace` | Deduplicate and stop several process trees. |
| `quick_restart` | Stop a listener and start an allowlisted development command. |

Blocking OS operations run through Tauri's blocking runtime. Metrics use a persistent, mutex-protected `sysinfo::System` snapshot because CPU usage requires a delta between refreshes.

## Port discovery

The Windows adapter runs `netstat.exe -a -n -o`. Rust then:

1. accepts only TCP rows in the `LISTENING` state;
2. parses IPv4 and bracketed IPv6 endpoints;
3. groups dual-stack entries by PID and port;
4. records all bind addresses on one logical listener;
5. joins listener data with a process snapshot.

The `-p tcp` netstat filter is intentionally not used because it can omit TCPv6 listeners such as Vite on `[::1]:5173`.

## Project recognition

Recognition starts at the process working directory and checks a limited number of ancestors for:

- `package.json` and a `dev` script;
- `go.mod` and Gin dependencies;
- `Cargo.toml`;
- a `.git` root used as the workspace name.

Known editor processes such as VS Code and Cursor are classified as developer tools before manifest inspection. This prevents an editor opened in a repository from being mistaken for that project's runtime.

## Process trees and workspaces

Tree traversal follows parent PIDs until it reaches a boundary such as PowerShell, Windows Terminal, VS Code, Cursor, or Explorer. It then walks descendants with explicit depth and node limits.

`go run` needs special handling: its temporary listener executable is controlled through the parent `go.exe` runtime, while the terminal and editor remain alive.

Workspace termination includes project runtimes but excludes editor tooling.

## Port reservations

Reservations are persisted locally in the frontend and identify owners by recognized project name, with the working directory as fallback. A background scan runs every four seconds. When another process owns a reserved port, the UI shows a collision banner and sends a native notification through the Tauri notification plugin.

Automatic termination is disabled by default and enabled separately for each reservation after explicit confirmation. This is reactive protection: a normal desktop application cannot prevent the operating system bind before it happens without owning the port or installing a lower-level service.

Vite fallback detection is a separate heuristic. If the reserved owner is still active and another Vite project listens within `reserved port + 1..10`, the UI reports a probable fallback. It sends a notification but never auto-kills the fallback process because that process did not take ownership of the reserved port.

A process-start watcher supplements socket discovery for short-lived runtimes such as Go. While reservations exist, the frontend polls a persistent process snapshot every 750 milliseconds. Newly observed development processes are checked for port hints in command arguments and bounded configuration files. Matching events are explicitly labeled probable because this mechanism observes process/configuration evidence rather than the operating system's `bind()` call.

## Security boundaries

- Command arguments are generated by Rust, not interpolated from frontend shell text.
- PID `0`, PID `4`, and Tatas Killer's own PID are protected.
- Bulk operations enforce PID count limits and deduplicate runtime roots.
- Kill success is verified against a new process snapshot.
- Restart directories are canonicalized and must exist.
- Restart commands must exactly match an allowlisted preset.
- Tauri capabilities should remain minimal as new plugins are added.
- Native notification access is limited by the `notification:default` capability.

## Cross-platform direction

Future OS adapters should implement a shared internal listener/process interface:

```text
PortScanner
|-- Windows: netstat / Windows APIs
|-- macOS:   lsof
`-- Linux:   /proc, ss, or lsof
```

Platform-specific discovery and process-control code should move out of `lib.rs` into `platform/windows.rs`, `platform/macos.rs`, and `platform/linux.rs` before those adapters are added.
